Algorithm Design

How SmartScholar works

SmartScholar uses keyword searching, optional filters and sorting to help users discover relevant academic articles from our XML dataset.

1. What problem does the algorithm solve?

Academic datasets can contain many articles with different research topics, publication years, journals and citation patterns. Finding relevant literature can become time-consuming when users have to examine every article individually.

SmartScholar addresses this problem by allowing users to search and narrow down the dataset according to their research needs. Instead of displaying every article without distinction, the algorithm checks the user's criteria and returns articles that match the selected conditions.

The current project uses a dataset of 50 academic articles. The algorithm processes the article metadata and organises matching results according to the user's preferences.

2. How the dataset supports the algorithm

The algorithm depends on the way information is structured in our XML dataset. Each article contains metadata that the algorithm can access and use when searching or filtering.

  • Title, keywords and topic: Used to find articles related to the user's search term and research interests.
  • Year: Used to check whether an article falls within the selected publication year range.
  • Open-access status: Used to identify articles marked as openly accessible.
  • Citations per year: Used to rank articles when the user selects citation-based sorting.
  • Journal: Included in keyword searching so users can also find articles through journal names.

We chose XML because it allows each article and its metadata to be represented in a structured format. Python can read the XML elements and retrieve the information required by the algorithm. This connection between the data model and the search conditions makes the dataset suitable for our purpose.

3. Search logic and optional filters

The algorithm is designed to make the keyword search and filtering flexible. Users can search with a keyword alone, apply filters without entering a keyword, or combine the keyword with any combination of the available filters.

Keyword search

The algorithm searches the article title, topic, journal and individual keywords recorded in the XML dataset. It converts the search input and searchable text to lowercase to make matching less sensitive to differences in capitalisation. A keyword match is found when the user's search term appears within at least one of these fields.

Topic filter

When a topic is selected, the algorithm checks the article's topic against the selected value. Articles that do not match the chosen topic are excluded. If no topic is selected, this condition is skipped.

Year range filter

The start year and end year are optional. When a start year is provided, articles published before that year are excluded. When an end year is provided, articles published after that year are excluded. If only one year boundary is selected, only that boundary is applied.

Open-access filter

When the user selects the open-access preference, the algorithm includes only articles whose open_access field is marked as true. When this preference is not selected, the algorithm does not exclude articles based on their open-access status.

Citation sorting

Citation sorting changes the order of the matching articles rather than filtering them out. In the current implementation, the algorithm sorts by citations per year, with the highest value first. If citation sorting is not selected, the matching results are shuffled into random order.

4. How the algorithm works:

  1. Load the dataset. Read the academic articles from the XML file using the dataset-loading function.
  2. Receive the search criteria. Store the keyword, selected topic, year boundaries, open-access preference and sorting choice in variables.
  3. Prepare the search input. Remove unnecessary whitespace from the keyword and convert it to lowercase.
  4. Iterate through the articles. Use a loop to examine each article and retrieve the metadata needed for searching and filtering.
  5. Apply the active conditions. Check the keyword and each selected filter. If an article fails an applicable condition, skip it and continue to the next article.
  6. Collect matching articles. Add articles that pass all applicable filtering conditions to the results list.
  7. Sort the results. Sort by citations per year in descending order when citation sorting is selected. Otherwise, shuffle the results randomly.
  8. Return the results. Return the matching article elements so that the website can display them to the user.

This process is repeated for every article in the dataset. An article is included only if it satisfies all the filtering conditions that the user has activated.

5. Example: combining search criteria

Imagine a user wants to find articles about artificial intelligence published between 2022 and 2026, prefers open-access publications and wants to see the most cited articles first.

  • Keyword: artificial intelligence
  • Topic: Artificial Intelligence
  • Year range: 2022–2026
  • Open access: Required
  • Sorting: Highest citations per year first

The algorithm checks each article against these conditions. An article must match the keyword in one of the searchable fields, match the selected topic, fall within the year range and be marked as open access. Articles that fail any of these active conditions are skipped. The remaining articles are then sorted by citations per year.

This demonstrates how multiple conditions can work together. The user does not need to apply every filter, and clearing a filter removes that particular restriction from the search.

6. Variables, selection and iteration

These algorithmic concepts are used to demonstrate how variables, iteration, and conditional selection support the systematic processing of a dataset and the identification of academic articles that meet specific search criteria.

  • Variables: Variables such as keyword, topic, start_year, end_year, open_access, sort_by and results store the user's input and the articles being processed.
  • Iteration: The for loop processes the articles one by one, applying the same search logic to each article.
  • Selection: The if statements evaluate the search criteria. The continue statement skips an article when it fails a condition.
  • Lists: The results list stores the articles that match the active conditions before they are returned.
  • Sorting: The sort method orders matching results by their citation rate, while random.shuffle changes their order when no citation sorting is selected.

The filtering conditions use AND logic: when several restrictions are active, an article must satisfy all of them to remain in the results. The keyword and the filters can therefore be combined without requiring users to select every available option.

File structure and project organisation

SmartScholar is organised into separate files and folders, with each file responsible for a specific part of the application. This separation makes the project easier to understand, maintain, test and develop collaboratively. The dataset, data-loading logic, search algorithm, website routes and presentation are kept separate rather than being placed in one large file.

What each file and folder does

  • Data/articles.xml — The dataset. This file stores the academic article records and their metadata, such as titles, keywords, topics, publication years, journals, open-access status and citation information. It provides the information that the algorithm processes.
  • src/read_xml.py — Data loading. This module reads the XML file and extracts the article elements into a format that the Python application can process. Keeping this task separate means the search algorithm does not need to contain all the XML-reading code itself.
  • src/search_articles.py — Search algorithm. This module contains the main search logic. It calls load_articles() to obtain the dataset, checks each article against the user's keyword and selected filters, collects matching articles, and sorts or shuffles the results before returning them.
  • app.py — Application and routes. This file creates the Flask application and defines the routes that users visit. It receives form input from the website, calls the search function when needed, and passes the results to the appropriate HTML template using Flask's render_template() function.
  • templates/ — Website pages. This folder contains the HTML templates rendered by Flask. The homepage provides the search interface, while the algorithm, dataset and people pages explain the project, its data and the team. The shared navigation bar is included in the relevant templates.
  • static/css/style.css — Presentation. This file controls the website's visual appearance, including layout, spacing, typography and styling. Separating CSS from HTML makes the design easier to maintain and update.
  • static/img/ — Images. This folder stores the images used throughout the website, such as the illustration on the algorithm page.
  • requirements.txt — Dependencies. This file lists the Python packages required to run the application, allowing the development environment to be recreated more consistently.

How the files work together

  1. The user opens the website and submits a search through an HTML form.
  2. app.py receives the submitted values through the relevant Flask route.
  3. The route calls search_articles() in src/search_articles.py, passing the keyword and selected filter values.
  4. The search module calls load_articles() from src/read_xml.py to obtain the article records from Data/articles.xml.
  5. The search algorithm checks the records, applies the selected conditions and prepares the matching results.
  6. The search function returns the matching articles to app.py.
  7. Flask passes the results to the HTML template, which displays the articles to the user.

Why we separated the responsibilities

This structure follows the principle of separation of concerns: each component has a clear responsibility. The XML file stores the data, the data-loading module reads it, the search module processes it, Flask handles requests and routes, and the templates and CSS present the results.

This makes the project easier to maintain because a change to one component does not necessarily require rewriting the others. For example, we can improve the search algorithm without redesigning the entire website, or update the website's styling without changing the filtering conditions. It also makes collaboration easier because team members can work on different parts of the project with clearer boundaries.

8. Why we designed it this way

We chose a rule-based search algorithm because our main goal was to make the academic dataset searchable and to demonstrate how an algorithm can process structured information. The conditions are explicit and relatively easy to understand, test and explain.

Making the filters optional gives users more control over their searches. For example, someone who knows a specific keyword can search directly, while someone exploring a research area can start with a topic or year range.

We use citations per year for ranking rather than total citation count. Older articles have generally had more time to accumulate citations, so citation rates can provide an additional perspective when comparing articles of different ages. However, citation rates do not completely remove differences between research fields, article types or publication contexts.

When citation sorting is not selected, the algorithm randomises the matching results. This offers a different ordering of the results, although it does not mean the articles have been ranked by relevance.

9. Collaboration and version control

To support collaborative development, we created a branch protection rule for the main branch in GitHub. The rule requires at least one approving review before a pull request can be merged into the main branch.

This encourages team members to review each other's changes before they become part of the shared version of the project. Code review can help identify mistakes, improve consistency and reduce the risk of introducing problems into the main branch.

Branch protection does not automatically prevent every merge conflict. Instead, it supports a more controlled workflow in which changes are reviewed and conflicts can be identified and resolved before merging.

10. Current limitations

  • Dataset size: The current dataset contains 50 articles, so the results cannot represent the entire academic literature.
  • Keyword matching: The search uses text matching rather than understanding the meaning or context of a query. It may miss relevant articles that use different terminology.
  • Citation indicators: Citation rates can change over time and vary between research fields. They should not be treated as a direct measure of research quality.
  • Random ordering: Results may appear in a different order when citation sorting is not selected. Random order does not indicate which articles are most relevant.
  • Data quality: The accuracy of the results depends on the completeness, consistency and correctness of the article metadata.

11. Future improvements: analysing research trends

In the future, SmartScholar could be extended beyond searching individual articles to provide an overview of the dataset on the homepage. This would help users understand patterns in the collected data and explore how research activity changes over time.

Statistical overview of the dataset

The homepage could display charts showing the number of articles associated with each research topic, publication activity by year and the proportion of open-access articles. These visualisations would help users understand the composition of the dataset without having to search through each article individually.

Identifying emerging research topics

By counting the number of articles published on each topic per year, the system could identify topics with increasing publication activity. Calculating percentage changes or comparing publication trends over several years could help users identify areas that may deserve further investigation.

Such patterns could indicate growing research activity, but they would not necessarily prove that a topic is becoming more popular among all researchers. The results would depend on the coverage and quality of the dataset.

Comparing citation patterns and publishers

Another improvement could be to compare citation rates, publication volumes and open-access proportions across journals or publishers. These comparisons could help users explore how publication patterns differ across the dataset.

However, a publisher or journal should not automatically be considered more trustworthy because it has more citations. Assessing trustworthiness would require additional evidence, such as peer-review practices, editorial standards, transparency and publication policies.

A more advanced recommendation algorithm

In a later version, SmartScholar could calculate a recommendation score for each article. The score could combine several factors, such as keyword relevance, topic similarity, publication recency and citation indicators. Articles with higher scores could then appear first.

This would introduce a more advanced ranking method while keeping the system explainable. The weights assigned to each factor would need to be tested and justified, because different research needs may require different priorities.

How mathematics could support these improvements

  • Frequency and percentages: Count articles by topic, year, journal or open-access status to describe the dataset.
  • Growth rates: Compare publication counts across years to identify changes in research activity.
  • Statistical comparisons: Examine citation distributions and publication patterns across different topics and journals.
  • Weighted scoring: Combine multiple article characteristics into a score to rank results according to the user's needs.

These improvements could develop SmartScholar from a basic search and filtering tool into a data-driven academic discovery system. The existing XML dataset and search algorithm would provide the foundation for these future developments.
